# Deploying UNSTABLE FORGE for ₹0

The application is a long-lived Express server (it serves the built Vite app and
`/api`, writes uploads, and holds a PostgreSQL pool). It cannot run on GitHub
Pages, which only serves static files, and it cannot run on a serverless/edge
platform without rewriting the database layer and the uploader.

This is the free architecture that runs the app as written:

| Piece | Service | Free terms, checked November 2026 | Cost |
| --- | --- | --- | --- |
| Web (Express + built SPA) | Render, free web service | No card required. Sleeps after 15 idle minutes, wakes on the next request (~1 min). 750 instance hours/month per workspace, spun-down time is free. Custom domain + managed TLS included. | ₹0 |
| Database | Neon, free project | 1 GB, no card, no expiry, scales to zero after ~5 idle minutes and wakes in under a second. | ₹0 |
| Uploads | PostgreSQL (`media_blobs`) | Bytes are stored in the database, because the free web tier has no persistent disk. | ₹0 |
| Domain | `*.onrender.com` subdomain | Free. A custom domain is also free to attach on Render; the domain registration itself is the only thing that would cost money. | ₹0 |

Not used on purpose: **Render's own free PostgreSQL**. It is deleted 30 days
after creation (14-day grace, then the data is gone), which would destroy C³
registrations. Neon's free project does not expire.

## 1. Database — Neon

1. Create a free project at <https://neon.tech> (GitHub sign-in, no card).
2. Copy the **pooled** connection string. It looks like
   `postgresql://user:password@ep-xxx-pooler.ap-southeast-1.aws.neon.tech/neondb?sslmode=require`.
3. Keep `?sslmode=require` — `server/db/index.js` turns TLS on when it sees it.

Schema, migrations and the seed event are applied automatically on boot, so the
database starts empty and initialises itself.

## 2. Web service — Render

1. Push this repository to GitHub (the blueprint on `main` is what Render reads).
2. In Render: **New → Blueprint**, choose the repo, apply. It reads `render.yaml`
   and creates the `unstable-forge` web service.
3. Set the values marked `sync: false` in the service's **Environment** tab:

   | Variable | Value |
   | --- | --- |
   | `DATABASE_URL` | the Neon connection string from step 1 |
   | `APP_URL` | the final public origin, e.g. `https://unstable-forge.onrender.com` |
   | `ADMIN_EMAIL` | the organiser account to seed on boot |
   | `ADMIN_PASSWORD` | a strong password — this is the first way in |

   `AUTH_SECRET` is generated by Render. Optional, and safe to leave unset:
   `RESEND_API_KEY` + `EMAIL_FROM` (verification and password-reset mail),
   `RAZORPAY_*` (payments), `GOOGLE_CLIENT_*` (Google sign-in). Without them the
   app degrades honestly: it never pretends an email was sent, never offers a
   payment method it cannot take, and hides the Google button.
4. Deploy. `GET /api/health` reports `database.engine: postgres` once Neon is
   reachable.

## 3. Custom domain (optional, still ₹0 to attach)

Render → the service → **Settings → Custom Domains** → add the domain, then
point the DNS record Render shows you (CNAME for a subdomain, ALIAS/A for an
apex). TLS is issued automatically. Afterwards change `APP_URL` to the custom
domain and redeploy, because Google OAuth callbacks and email links are built
from it.

## 4. Third-party callbacks to register

Replace `APP_URL` with the real origin:

- Razorpay webhook: `https://<origin>/api/payments/razorpay/webhook`, events
  `payment.captured`, `payment.authorized`, `payment.failed`.
- Google OAuth redirect URI: `https://<origin>/api/auth/google/callback`.

## 5. What to verify after the first deploy

- `/api/health` returns 200 with `engine: postgres`.
- `/brief` lists 11 challenge domains (they load from the API, not the fallback).
- Sign in with the seeded `ADMIN_EMAIL`, open the organiser console, upload an
  event image, reload — the image still resolves after the service sleeps and
  wakes (that is the database-backed upload path).
- Register a test participant, then delete the test registration.

## Free-tier behaviour to plan around

- **Cold start.** The first request after 15 quiet minutes takes about a minute.
  Before the event opens, ping `/api/health` every 10 minutes from a free cron
  (e.g. cron-job.org) to keep it warm.
- **750 instance hours/month.** A service that is awake around the clock would
  use ~730, which fits, but leaves little headroom for deploy restarts. If the
  workspace exceeds the quota, free services are suspended until the next month.
- **No persistent disk** on the free tier: `MEDIA_DIR` is a cache, and the real
  copy of every upload lives in `media_blobs`, so nothing is lost on restart.
- **No backups** on free tiers. Export registrations from the organiser console
  before the event and keep the CSV.
- **Postgres on Neon** scales to zero after ~5 idle minutes; the first query then
  takes a fraction of a second, which is invisible next to the web cold start.

## Moving off free later

The same blueprint scales without code changes: upgrade the Render service to
remove spin-down, move `DATABASE_URL` to a paid Neon plan or any managed
PostgreSQL, and optionally attach a Render disk (paid) if you would rather keep
uploads out of the database.
